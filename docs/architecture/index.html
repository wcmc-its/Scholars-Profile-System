Headshots load live at read time straight from the WCM directory (directory.weill.cornell.edu) — never stored, never via the ETL. Write-backs: the nightly etl:orcid-push copies confirmed ORCID iDs back into WCM Identity through the ReCiter engine API, the ETL's only write to a WCM system of record (prod only; staging runs it as a dry run). The app writes to ReciterAI only for core-claim mirrors and the opportunity SUBMISSION queue. ReciterAI scores, topics, tools and grants refresh nightly, spotlights weekly, and the topic hierarchy on the annual run (Jul 1, behind a manual approval gate). Some ReciterDB-side data (ed, mentoring, citations, clinical-trials) reaches the in-VPC ETL as NDJSON bridge files in ReciterAI's S3 bucket rather than as direct reads. Faculty Review Tool self-reported mentees are read weekly from the COI portal's SQL Server (etl/frt) and feed /edit mentee suggestions. POPS (the public weillcornell.org physician directory) enriches clinical scholars with board certifications, specialties, and expertise (etl/pops/index.ts) — it keys off the clinical-profile flag Enterprise Directory sets, runs weekly (PopsWeekly) after the nightly ED pass has set that flag, and feeds the people search index. Grant enrichment runs weekly: NIH RePORTER (PI profiles from the public API, plus RePORTER-derived tables in ReciterDB), NSF awards, and the Gates Foundation's public committed-grants CSV. PubMed E-utilities stamp retracted papers nightly; the NLM MeSH descriptor download (etl:mesh) is on-demand, not scheduled. Clinical trials originate in OnCore (the CTMS — a manual institutional export, static until the next export lands). OnCore's export stages into reciterdb (clinical_trials); the weekly etl:clinical-trials reads that list and fetches each NCT live from ClinicalTrials.gov API v2, falling back to reciterdb's clinical_trials_enriched row only when a batch fails. CTL portfolio (available technologies) is WCM's own Center for Technology Licensing, scraped weekly from its public portal (innovation.weill.cornell.edu). WCM Newsroom is read weekly for articles that mention a scholar (news.weill.cornell.edu/news/feed.json, etl/news/*) — one paginated JSON read covers the archive back to 1997. A vivo.weill.cornell.edu link in the article body publishes the mention outright; a prose name-match queues it for human review in /edit. The Research office's news page (research.weill.cornell.edu/about-us/news-updates) is a syndication target of the newsroom, not a source — SPS scraped it until #2200/#2231. Media clips: External Affairs' daily 'WCM in the News' digest is mailed to an SES inbound address (cdk/lib/inbound-mail-stack.ts), and etl:news-clips parses it nightly into pending mentions for comms review; the Research Dean's weekly funding digest arrives the same way and etl:funding-digest feeds it to the ReciterAI submission queue (Views 6 and 7; prod only, staging is a dry run). Honor-society rosters are scraped from public lists on their own Step Functions machine (Mon 10:00 UTC), not the Sunday weekly chain; every match is human-reviewed. Also read over public HTTPS: the ORCID registry (weekly; advisory /edit/orcid-coverage only). CTSC roster feed (the Clinical & Translational Science Center's investigators-and-trainees feed, the one the ReCiter Institutional Client reads) mirrors the ctsc center roster nightly (etl/ctsc-roster). It is not a publication source: its PubMed IDs are never read, and its CWIDs are checked against Enterprise Directory before a member is linked.

View 4 · edge topology — both envs live (#502)

Edge topology — NetScaler live in both environments

NetScaler is live in both environments (staging 2026-07-21, prod 2026-07-24). CloudFront sends every behaviour plus the default through the NetScaler VIP → app ALB, except /_next/static/*, which an origin group serves from a private S3 bucket (OAC, written additively by the deploy, 14-day lifecycle) and falls back to the ALB on 403/404 (#700). The origin leg is HTTPS-only (an HTTP origin behind the VIP's HTTP→HTTPS upgrade loops forever — the original ERR_TOO_MANY_REDIRECTS bug), and NetScaler dials the ALB on :443, forwarding the X-Origin-Verify header CloudFront injects. Durable in CDK via the #1507 origin-flip (PR #1852 staging, #1926 prod). The WAF runs the #461 WCM-only gate (branded 403), enforced AWS managed rules, Bot Control in label-only mode and a 5000/IP rate limit (branded 429), and it writes WAF logs. The cache key carries Next 16's _rsc param and the RSC/Next-Router-* headers (#2962/#2965). Writes that suppress, rename or revoke purge the edge through CreateInvalidation (#353/#828), and the cdn-reconcile ETL retries any purge still pending. Port corrected 2026-07-25 — this view previously said :80 and called the ALB :443 listener an unused guard; re-measurement (VPC flow logs + a timed causal probe) showed :443 is the live leg in both envs. The :443 TLS policy is now at parity — both envs carry the #1929 AEAD-only pin, staging deployed 2026-07-27 (#1937).

View 5 · inside the app (C4 component)

Application internals

Inside the single Next.js container: the public pages and staff /edit UI (React Server Components), the API route handlers grouped by purpose — the public-data surface spans scholars, publications, topics, methods, centers / units, NIH portfolio, funding opportunities, the center-collaboration network, and capped exports — and the internal libraries they share, wired to Aurora (reader/writer), OpenSearch (five per-entity aliases), the SAML IdP, and the WCM directory (LDAP role groups + live headshots); scoped grants and the audit log live in Aurora. ISR output is shared across tasks through an S3 cacheHandler (#1503). The /edit write path calls Amazon Bedrock for AI generation (overview · biosketch · CV) and Matcha concept extraction; reads ReCiter suggestions and writes opportunity submissions and core claims to ReciterAI's DynamoDB (rejects reach the ReCiter engine through the ETL); and reflects each commit post-response — ISR revalidate, CloudFront invalidation, OpenSearch suppression. The CV path reads clinical fields live from POPS (lib/edit/pops.ts). proxy.ts (Node runtime) gates /edit and impersonation, sets CSP on every document, and 301s legacy VIVO URLs.

View 6 · the grant-matching subsystem at a glance

Grant matching — system context

How a funding opportunity travels from its source to a researcher's screen: ReciterAI's pipeline_grants fetches, judges, and persists the corpus into account-shared stores (DynamoDB reciterai + S3), SPS's nightly projection mirrors it into Aurora and the scholars-opportunities index, and the Grant Matcha surfaces serve it — with a staff intake loop and a weekly Research Dean funding digest feeding URLs back into the same pipeline, and freshness guardrails watching the whole supply chain.

Cadences: the ReciterAI ingest runs daily at 03:00 UTC (EventBridge → Fargate, reciterai-grants, shipped 2026-08-20 closing ReciterAI#269's gap); SPS projects in the nightly at 07:00 UTC in prod (07:45 in staging, offset so the two envs' InfoEd steps never overlap) — a 4-hour launch gap in prod, measured on first tick. SPIN is manual-only until the license question on scheduled bulk pulls clears (its weekly rule is spec'd but deliberately unshipped). WCM funding DB is frozen — its one-off crawler left no code; SPIN overlap is being measured before deciding rebuild vs retire. The submission drain is DynamoDB-only: it never publishes the S3 artifact (a per-run publish would trip the sweep's shrink guard). Suppression is a soft-delete the nightly upsert can never resurrect — the upsert's column list simply never names the three suppress* columns. The grants-for-me card rides SELF_EDIT_GRANT_RECS (staging-on, prod-off). The funding digest (etl:funding-digest, weekly Sunday step) submits each new link from the Research Dean's email to the same SUBMISSION queue; its dedup is stricter than the panel's, and only prod submits — staging dry-runs because the queue table is shared. Liveness: the nightly also reads grants/latest/manifest.json and writes its generated_at as a ReciterAI-grants run row (fail-soft), graded on /edit/etl-status beside the 21-day corpus-age alarm.

View 7 · supply chain + guardrails

Opportunity corpus pipeline & freshness

Inside the daily corpus run: every source funnels through one normalize → dedupe → gate → LLM judge → persist chain in the reciterai-grants Fargate task, with the SPS submission drain chained after it. Three independent signals watch it: a log-error alarm on the producer (the ; chain means a grants.gov failure never reaches the exit code), the per-source freshness metric + ≥21-day alarm on the SPS side, and the manifest-age liveness row on /edit/etl-status (a status row, not an alarm).

Why two alarms: the freshness metric's corpus-wide series goes green when any source lands a fresh row (a manual drain once masked three 45-60-day-stale feeds), so the per-source dimensions exist for per-feed alarms once each cadence proves out; the log-error alarm covers failures the exit code can't (the ; chain deliberately lets the drain run after a grants.gov crash). Drain is DynamoDB-only: on 2026-08-20 the old drain-side publish clobbered grants/latest with a 65-item subset — exactly what the shrink guard exists to refuse — so the drain no longer publishes at all. SPS reads the corpus from DynamoDB; from the artifact it reads only grants/latest/manifest.json, as the producer's liveness trace. The queue has two writers: the /edit/grant-matcha intake panel and the weekly Research Dean funding-digest step; only prod submits, because the table is shared. SPIN runs manually until the license check on scheduled pulls clears (weekly rule spec'd, deliberately unshipped). The 03:00→07:00 UTC gap (07:45 on staging) is a launch gap; first-tick wall-clock vs 07:00 is a monitored assumption, and Fargate has no task timeout — a hung run runs until noticed.

View 8 · who asks, which engine answers

Matching surfaces & engines

The three grant-matching surfaces and the engine each one rides: Grant Matcha's seeded ask and /edit/matcha's plain ask share the people spine (LLM extraction → cluster retrieval → RRF fuse), the dark grants target awaits a UI consumer, and the self-service card uses the no-LLM forward matcher over the opportunities index plus the scholar's Aurora topics and MeSH fingerprint. The route persists each people-target answer in Aurora and replays it with an asOf date until Re-run. Eligibility is deliberately split: “what a grant requires” is extracted upstream by ReciterAI; “does this researcher qualify” is the client-side rail — the single owner since the find-researchers sunset, fed by the esiEligible signal the people spine derives from Aurora on the grant-matcha path only.

Retired 2026-08-20 (Phase 3): /edit/find-researchers and its structured reverse matcher (rankResearchersForOpportunity survives only for two measurement scripts); its abstain floor (GRANT_MATCHER_ABSTAIN_FLOOR) is deleted outright — the ask card's thin-match caution (from assessMatchSignal) is the surviving low-signal warning. Suppression semantics: browse/detail hide a suppressed opportunity immediately (Aurora reads); index-backed surfaces — both spines' retrieval and the forward matcher — lag by one nightly rebuild, stated in the suppress dialog. Cost shape: every spine ask bills Bedrock Sonnet (the task role is deliberately scoped to Opus/Sonnet only — there is no cheap-model tier), which is why the in-RAM result cache and the persisted per-search answer (#2630: served with an asOf date, Re-run forces a fresh run, no expiry; degraded runs are never stored) exist. The grants spine serves target:“grants” behind GRANT_MATCHA with its own cache namespace and is not persisted; its result-card UI was deliberately reverted pending the convergence eval.
