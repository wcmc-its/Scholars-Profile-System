Apollo Surface Language

A design touchstone for the /edit console. Governs which surface sits on what — deliberately separate from the existing Apollo Editor Colour Language docblock, which governs which hue means what. Values below are copied verbatim from app/globals.css on origin/master; if they drift, the app is right and this file is stale.

R2 — A fill step is never a boundary. The hairline is.

Every fill step in this palette is under 1.13:1. None of them separate anything on their own, so any change of level carries a border. This is the rule the console is actually breaking; the fill choices were mostly fine.

Resolved — rail moved off thead. But it is three values, not one. I called this a "one value edit". That was wrong, and here is why:
  • --apollo-rail #f4f1ed → #ede7df — the actual decision.
  • --apollo-rail-hover must move too. The old hover #ece7e1 lands at 1.001:1 against the new rail — the hover state would disappear entirely. → #e4ddd2, which preserves the 1.09 hover feel.
  • --apollo-rail-border must move too. --apollo-border #e9e3df reads at 1.035:1 on the darker rail — the edge dies. → --apollo-border-strong #dbd3cd at 1.203:1.

Corollary to R2: the darker the fill, the stronger the border it needs. A hairline tuned for white is not a hairline on greige.

Consequence to weigh: this also darkens the Matcha rail (matcha-panel.tsx:1361), which you signed off in #1806. I think it is an improvement and keeps one rail treatment across the console — but it is a change to shipped work, so it is your call, not mine.

R5 — Uniform records are rows, not cards.

If every item carries the same attributes in the same order, use a table. Reserve cards for heterogeneous items, or where one item is the subject of the page. "Your editable units" at the top of Org units is legitimately a card list — it is 1–3 items and they are the subject. The "All units" audit below it is not.

R7 — The row is the target, not a link on the right

Hover any row above. The whole row is clickable, but it is still a real <a href> — not an onClick on the <tr>. That distinction is the whole rule; the naive version silently breaks four things.

The implementation is a stretched anchor, never a row handler.

Put a real <a href> on the primary cell and let it cover the row:

tr        { position: relative; }
a.primary::after { content: ""; position: absolute; inset: 0; }
tr:hover  { background: var(--apollo-surface-2); }
tr:focus-within { outline: 2px solid var(--apollo-maroon); outline-offset: -2px; }

Two costs, and the carve-outs

The stretched anchor is not free. Both costs are real and both have a fixed answer.

Any other interactive element in the row gets position:relative; z-index:1. Without it, the row link eats every button in the row — the single most common way this pattern ships broken.

Cost 2 — text selection dies inside the row.

The overlay means you cannot drag-select a CWID or a unit code out of the table. Accept it on navigational tables (Org units, Funding matcher, Profiles). Do not use R7 where the table exists to be read and copied from — an audit or export view — or where a row has two equally-primary destinations, in which case there is no single target and explicit links are correct.

R6 — A filterable attribute must be visible on the row.

Funding matcher filters by Deadline and Sponsor, but shows neither on the card. A filter whose effect you cannot see reduces to guesswork — the same failure as an invisible selected facet, one layer up.

Known debt — --apollo-surface-2 has the disease the rail had.

It does three jobs: thead, chip fill, ghost-hover. A chip on a thead, or a ghost-hover on a surface-2 ground, lands at 1.000:1 — the same collision that forced the rail split. Until it is split, the rule is: surface-2 elements never sit on surface-2; hover on greige uses --apollo-rail-hover. Also note --apollo-rail-border and --apollo-border-strong are the same hex — alias the former to the latter before they drift.

Not governed here: hue-to-job (BRAND / YOURS / LOCKED / DANGER / INFO / ELIGIBILITY) — see the Apollo Editor Colour Language docblock at app/globals.css:89-126. Keeping the two separate is deliberate; merging them is how the first one got vague.

v2 — What staging taught us

Rules R8–R11 were added after reviewing /edit/units, /edit/administrators, and /edit/data-sharing on staging. All three pages follow the surface rules and still wash together — because the failures moved from surfaces to ink. The surface language was silent on ink; it no longer is.

R8 — Two inks per block

Every block gets at most two text colors: --apollo-ink for the thing itself (names, numbers, the sentence you came for) and --muted-foreground for annotation. On /edit/data-sharing the headline sentence, the methodology, the coverage note, and the section ledes are all the same muted gray — five levels of importance, one ink.

R8 — Ink for the subject, muted for the caption. Never a third gray.

If a block needs three inks, it is two blocks. Section descriptions, methodology notes, and captions are muted; the data, the headline sentence, and every value a user came to read are --apollo-ink.

R9 — Maroon has one job per view: the link

/edit/units sets unit names in maroon (links, per R7) and the word "Missing" in maroon (a status) and underlines the org codes (a second link style). Three jobs, one hue — the Description column reads as a column of links.

One primary link (R7). Codes are data. Gaps use --wrong with a glyph, matching the ✓/✗ audit columns already shipped.

R9 — In any one view, maroon marks the primary link and nothing else.

Status colors come from the colour language (--wrong, --right). A second destination in a row is a plain-ink anchor that underlines on hover — never a second maroon and never a resting underline. Corollary: maroon is never a border on repeated containers — /edit/administrators frames every person card in maroon, which spends the accent on chrome. (The scholar editor's single maroon left-rule on the active panel is different and correct — see R12.)

R10 — Before shipping a column or per-row badge, ask: does it ever vary on this page?

If not, it moves to the group band, the lede, or a footnote. This is R6's inverse: R6 says a filterable attribute must be visible; R10 says an invariant attribute must not be repeated.

R11 — Declare headers once per collection

/edit/administrators renders each person as a maroon-bordered card containing its own table — Org unit / Role / Source / Actions re-declared for every human on the page, with a radio group per row. The DEPARTMENTS band on /edit/units is the right pattern: one table, one header, group bands inside it.

R11 — Grouped uniform records are one table with group bands, not a card-of-tables per group.

The person becomes a band row (name · title · CWID, with per-person actions right-aligned in the band) on --apollo-surface-2, matching the DEPARTMENTS band. Column headers render once. Per-row controls stay per-row; per-person controls live in the band. Reserve the card-per-group form for when groups carry different columns — then they are not uniform and R5 no longer applies.

R12 — Selection is a maroon fill; there is one active panel

The scholar editor is the house's best page and it already has a selection language: the current nav item is a maroon fill with white text, the segmented choices (Third person / Formal / Standard) fill maroon when chosen, and one maroon left-rule marks the panel the nav item opened. That is the canon — write it down so other pages stop inventing.

/edit/scholar's "Grants for me" sorter and the reports sliders ship default blue — a hue with no job in the colour language, meaning "selected" only by accident.

✓ maroon fill = chosen, everywhere

One selection treatment across nav, segments, sort pills, checkboxes, radios, sliders, toggles: accent-color: var(--apollo-maroon) or a maroon fill. Matches the attribute rail and the Draft-with-AI segments.

R12 — Maroon has exactly two jobs: the primary link (R9) and the current selection.

Both mean "the one that matters here." Status, decoration, and repeated-container borders are still forbidden. The maroon left-rule is singular: it marks the active panel that the selected nav item opened — one per view, never on cards in a list. Form controls never ship UA-default blue; set accent-color globally.

R13 — Amber means "awaiting human judgment" — and it obeys R10

NCI Table 2a tags every row "AI-SUGGESTED" in amber; the reports pages are advisory top to bottom; the members view collapses suggestions into an amber pill. Amber is already converging on one meaning — a machine proposed this and a person has not yet ruled — which matches the facet-position hue and the "Needs review" queue.

R13 — Reserve the amber treatment for pending-judgment states, and hoist it when invariant.

When every row on a page is AI-suggested (Table 2a today), the per-row tag is an R10 violation — say it once above the table ("all percentages below are AI-suggested until confirmed") and tag only the exceptions once confirmations start landing. Confirmed values drop the amber; they do not gain a green — quiet is the confirmed state.

R14 — Every /edit route wears the shell

One reports page renders a bare table on white — no top bar, no nav, no page ground, no table frame. Advisory tools feel optional; chrome-less pages feel abandoned.

R14 — Shell (bar + nav + --apollo-page) is non-negotiable, reports included.

Reports are still R1/R2/R5 territory: warm page, framed tables, greige thead. The report-scoped controls (filters, sliders, downloads) sit in the content column under the report title, styled per R3/R12 — not floating in an unstyled void.
